# Carte product brief

Carte helps someone choose from an unfamiliar menu by translating names and descriptions into a spatial language of taste. The useful moment is a diner finding a dish or drink that matches their appetite, then keeping a small shortlist they can discuss with a server.

## Core experience

Photograph one or more menu pages. Review the extracted names, categories and prices. Open an illustrated quadrant, select a plate, wine or cocktail, understand its likely character, then save a choice for tonight. A reading-led menu view offers the same information in familiar rows.

The map changes its dimensions for each menu and item category. A broad wine list may use body and acidity. A list of aromatic whites may use aromatic intensity and acidity. Both dimensions should help distinguish the choices actually present. Axis changes are deliberate and visible; ordinary filtering never moves the remaining items.

## Visual identity

The interface resembles a small printed restaurant guide: warm paper, ultramarine line work, expressive serif titles, restrained metadata and useful white space. Glyphs depict the vessel or a defining ingredient. Short names remain beside the glyphs, so illustration recognition is never necessary to operate the app.

Menu margins is the default direction in the exported prototype. It places descriptive rows first and puts a miniature quadrant beside each item. Taste atlas is the discovery-led alternative. In the native product these can be views of one shared menu and shortlist; users should not experience separate data silos.

## First release

- Multi-page photo capture and photo-library import.
- Extraction review with editable names, categories, prices and currency.
- Category-specific axes, explained placements and explicit unknown positions.
- Taste-map and menu-list views with one shared selected item.
- Item details, menu evidence and conservative pairing suggestions.
- A per-menu shortlist with saved state and a known-price subtotal.
- Offline access to previously analyzed menus.

## Later releases

Add a personal taste journal using an explicit “Loved this” action, saved restaurant visits, a few remembered preferences and sharing a shortlist. Build preference learning only from user feedback. The first release does not need an account, public ratings, a discovery feed, ordering or payments.

## Product principles

Explain estimates with the source text. Preserve the original item name and currency. Let people correct extraction before analysis. Make uncertainty visible without burdening every item with a score. Keep related screens connected by the same small glyph, name and selection state.

Treat allergies, dietary requirements and alcohol content as a separate information problem. Missing menu text must remain unknown; taste analysis cannot certify safety or suitability.

## Success criteria for an early pilot

Measure whether users can find a plausible item and understand why it appears in its corner. Observe correction burden, selection time, use of explanations and whether the list view resolves map confusion. Establish a baseline with real pilot menus before choosing numeric performance targets. Review axis choices and placements with knowledgeable diners and restaurant staff.
